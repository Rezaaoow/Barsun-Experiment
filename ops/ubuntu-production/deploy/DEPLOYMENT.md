## Automated application updates

The initial production-approved ref records the explicitly verified deployment baseline. Future approval is produced only by approve-production after backend-tests succeeds on a main commit from this repository. The workflow only fast-forwards that ref; older completed CI cannot replace a newer approval. The server fetches using its read-only GitHub SSH identity every two minutes, verifies approval is an ancestor of main, and deploys only that frozen SHA. No GitHub administrator token or server SSH private key is stored in Actions.

Installed root-owned release.py handles application files only; it does not self-update privileged operations code from Git. Real active incomplete research runs defer unattended deployment. Explicit operator --allow-active is available only for a deliberately selected maintenance action. Dependency changes stop for a separately validated runtime rather than silently installing new packages. A successful encrypted backup is required before switching; immutable source hashes, local DB/startup guard and app health are checked. Failure restores previous CODE and checks health, leaving database contents intact. Operator rollback selects the recorded previous release and never silently restores an old database. Keep current/previous and one extra release to bound source storage; cleanup occurs only after backup and health succeed.

The server logs deployment status locally. Same-server status has no external delivery channel configured. Local application, backup age, root free space and backup-volume reserves are checked each minute. Journal namespace is capped at 64 MiB; dedicated privacy-safe Nginx logs rotate at 8 MiB with four rotations, checked every five minutes. Rotation thresholds are not hard per-minute write limits. PostgreSQL's existing OS rotation policy remains intact.
