# Local Production backup and recovery

User approved local encrypted backups pending external storage, with particular attention to limited disk. New server 37.152.183.1 only. User explicitly chose a clean new Production database; do not import old studies, links, results or credentials. Old hosting remains untouched and operational.

The root filesystem is approximately 46 GiB with 42 GiB free before this step. A preallocated 4 GiB filesystem image provides a hard maximum for the local Restic repository and cache. It resides on the SAME physical disk and offers no independent disaster protection. Mount it with nodev,nosuid,noexec. A missing mount must abort backups, never silently write into the underlying root directory. Application startup must not depend on this mount/service.

Capture the local socket-only barsan_production database as postgres using pg_dump custom format with bounded lock wait and timeout. Include database globals, protected application configuration, installed service/Nginx/PG configuration, release metadata and offline runtime dependencies. Assemble sensitive temporary files only in /run (tmpfs), root-only and bounded per-file/process limits; clean temporary paths on success/failure. Never log contents, credentials, participant payloads or command error bodies containing SQL. Consistency of DB records comes from pg_dump; capture release/config under the deployment/backup operations lock so deployments cannot interleave with it. Old hosting is never contacted.

Store encrypted backups using Restic with a random password in a separate root-only file outside the backup image. Application/repository accounts cannot read it or alter backup resources. An off-server recovery-password copy remains pending; no secret is printed or committed. Local root compromise can expose/destroy both repository and password. Disk/server loss can destroy both live data and backups.

Timer every five minutes, persistent missed-run handling, one job at a time, bounded runtime/resource use and root free-space reserve of 8 GiB. Normal backups stop below that reserve. Before capture, require sufficient backup-volume space for incoming files and prune workspace. Initial policy: all snapshots for six hours, hourly 24, daily seven, weekly four; always protect the latest snapshots. Pruning is scoped to this repository/host/tag and performed only after a successful backup or for space recovery when a verified snapshot already exists. Never mark success after failed dump, encryption, integrity check or pruning; never delete application data as backup cleanup. The 4 GiB hard cap can force backup failure as the DB/history grows; surface that condition instead of filling the application disk or silently shortening retention.

Root-only status records include last success, failure reason class, snapshot ID, byte usage/free space and off_server=false. Local journal records contain constant operational events only. Local status cannot notify an operator during complete server/network failure. Log rotation and a dedicated bounded journal namespace prevent unbounded application/job logs. Provider snapshots are not available through current access and are not claimed configured.

Recovery verification restores an actual backup into a uniquely named temporary database on this SAME Production server; no public Staging app is created. Verify table row counts and file hashes. Database creation/deletion is limited to a temporary database created by this operation, authenticated marker and expected owner. It never restores over barsan_production. Later application acceptance uses isolated barsan-test-* studies in the new Production app. Record measured recovery time. Pre-deploy backups precede app schema startup. Code rollback never silently restores an older database; schema/data recovery requires deliberate selection because newer responses would be discarded.

External extension: create a private remote Restic repository (S3/SFTP), copy encrypted snapshot history using Restic's repository-copy operation, add credentials as protected files and a separately monitored transfer job. Keep capture format/retention/deployment integration unchanged. Verify an actual remote restore before claiming off-server protection. An unsupported/absent remote destination is explicitly pending, not successful.

The bounded local system permits functional deployment and testing now. It does not provide zero data loss, point-in-time recovery, full-system recovery or independent disaster recovery. Healthy five-minute capture still leaves an interval plus execution-time loss window; failed jobs increase it.
