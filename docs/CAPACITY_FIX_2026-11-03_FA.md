# اصلاح ظرفیت پس از آزمون native ASGI

## نتیجهٔ جاری

Staging روی کد ثابت `7af1838` با دو Uvicorn worker، سقف هشت handler sync و pool چهار در هر worker فعال است. خطای رقابت شروع با قفل تراکنشی اصلاح شده است. دو آزمون کامل ۶۰۰جریانی، از HTTPS داخل هاست و از دو مبدأ، تکمیل دقیق داده و صفر شکست HTTP داشتند؛ p95 بیرونی آزمون دو مبدأ حدود ۱٫۲ ثانیه بود و هدف latency را نگذراند. آزمون API و تعداد محدود مبدأها معادل ۶۰۰ مرورگر/شبکهٔ واقعی نیستند. Production منتقل نشده و هیچ PRی merge نشده است.


هدف: رفع رقابت شروع اجرای یکسان و تعیین محل انتظار پیش از تغییر تنظیمات میزبان.

کد پایه: PR #25، e2b725cd0e1924d2dfcbb16f3cbb19d59496bd64. Staging: LiteSpeed → loopback Uvicorn دو worker؛ Production همچنان Passenger. گزارش قبلی در PR #26 ثبت شده است.

## تغییرات

- در لاگ بار قبلی ۱۶ خطای `RuntimeError: can't start new thread` پیدا شد. محدودیت واقعی NPROC حساب قابل خواندن نبود؛ خطای ساخت thread قطعی است، اما منشأ دقیق kernel/LVE هنوز اثبات نشده است. [CloudLinux](https://docs.cloudlinux.com/cloudlinuxos/limits/) threadها را در NPROC می‌شمارد و [Starlette](https://www.starlette.io/threadpool/) به‌طور پیش‌فرض تا ۴۰ thread در هر worker اجرا می‌کند. تنظیم اختیاری BARSAN_SYNC_THREADS=8 در launcher Staging تعداد درخواست‌های sync هم‌زمان هر worker را محدود می‌کند؛ event loop و صف درخواست‌ها فعال می‌مانند. پیش‌فرض برنامه بدون این env تغییر نمی‌کند.
- انتشار اول به‌دلیل بررسی health پیش از آماده‌شدن workerها برگشت خورد. در rollback، import هم‌زمان می‌توانست فایل dependency در حال بازگردانی را نبیند. روش بعدی سرویس را پیش از جابه‌جایی مجموعه فایل‌ها متوقف و برای readiness با retry محدود منتظر می‌ماند. کد قبلی و health Staging پس از rollback تأیید شدند.
- PostgreSQL: قفل تراکنشی شناسهٔ start_request_id و قفل ردیف assignment پیش از خواندن ledger/progress؛ SQLite: BEGIN IMMEDIATE پیش از خواندن.
- آزمون رقابتی درخواست یکسان، شناسهٔ تازه و حفظ run قبلی در SQLite و PostgreSQL مستقل CI.
- middleware خالص ASGI و ContextVar برای اندازه‌گیری درخواست و DB؛ پیش‌فرض خاموش، فعال‌سازی فقط Staging. لاگ خصوصی و چرخشی Supervisor، بدون هویت یا payload.
- بستهٔ runtime اکنون request_metrics.py را هم لازم دارد. launcher مقید به hash باید همراه فایل برنامه به hash نسخهٔ تست‌شده به‌روزرسانی شود؛ restart با Supervisor انجام می‌شود.

## وضعیت ابتدای این نوبت

health اصلی در شروع این نوبت بدون بار timeout داشت. بار سنگین تا تأیید سلامت پایه یا رفع علت متوقف بود. هیچ reset یا حذف داده‌ای مجاز نیست و تست PostgreSQL smoke هرگز روی دیتابیس اصلی یا Staging اجرا نمی‌شود؛ فقط دیتابیس disposable CI.

## تأیید نسخهٔ اصلاح‌شده

نسخهٔ ثابت `7af183881410faf5d089efefe44d71d43781d8ce` پس از CI موفق شامل تست PostgreSQL و تست هم‌زمانی روی Staging منتشر شد. readiness با retry محدود، سه health عمومی، hash فایل‌های برنامه و ثابت‌ماندن فایل‌های اصلی تأیید شدند. ۱۳ بررسی زنده، از جمله شش درخواست هم‌زمان برای هر شروع در پرسشنامه، DD، Frame و Control، گذشتند. شمارش دیتابیس ۲۵ پاسخ، ۳۰ DD، ۴۴ دور UT و چهار مرحلهٔ completed را تأیید کرد.

پس از راه‌اندازی مجدد Staging، health اصلی بدون restart Production دوباره پاسخ داد؛ شش probe متوالی سالم بود. علت سلامت متناوب قبلی هنوز قطعی نیست. بار ۱۰۰ نفر با trace و مقایسهٔ Server-Timing با waiting بیرونی آغاز شد؛ نتایج در حال جمع‌آوری است.

## آزمون عمومی ۱۰۰ نفر پس از اصلاح

۱۰۰/۱۰۰ سناریو تکمیل، صفر شکست از ۹۶۸۸ درخواست. شمارش مستقل: ۱۰۰ پرسشنامه/۲۵۰۰ ردیف، ۱۰۰ DD/۳۰۰۰ ردیف و ۱۰۰ UT/۲۲۰۰ ردیف؛ همه دقیق. p95 بیرونی ۶۸۳٫۱۳ms و p99 برابر ۱۲۲۲٫۰۲ms؛ آزمون به‌دلیل عبور p95 از هدف ۵۰۰ms با exit 99 تمام شد، نه خطای HTTP یا دادهٔ ناقص. p95 زمان ASGI برابر ۴٫۵۶ms، pool برابر ۰٫۰۳۴ms و waiting بیرون برنامه برابر ۶۸۰٫۰۲ms بود. تفاوت با baseline قبلی را نباید صرفاً اثر thread-limit دانست؛ مسیر شبکه و بار پس‌زمینه کنترل‌شده نیستند. آزمون عمومی ۶۰۰ در بخش بعد گزارش شده است.

## آزمون عمومی ۶۰۰ نفر پس از اصلاح

آزمون با دو timeout متوالی health اصلی از مبدأ Mac متوقف شد (exit 105) و نتیجهٔ پذیرش ظرفیت ندارد. ۲۸۰۶۱ تلاش HTTP و ۲۰۳ شکست transport با status=0، بدون پاسخ 5xx گزارش شد. شمارندهٔ تکمیل client صفر بود؛ زمان اجرا کوتاه شد و نباید آن را با یک آزمون کامل هم‌مدت مقایسه کرد. p95 بیرونی ۷٫۰۷s، p95 Server-Timing برنامه ۴٫۴۲۲ms، pool حدود ۰٫۰۳۱ms و SQL حدود ۲٫۷۵۱ms بود.

لاگ خصوصی در پنجرهٔ آزمون ۲۷۹۵۵ درخواست رسیده، همگی ۲۰۰، حداکثر سه in-flight در هر worker، p95 مدت ASGI برابر ۴٫۵۶۱ms و حداکثر ۱۱٫۳۸۳ms داشت. خطای جدید برنامه یا thread ثبت نشد. ساعت دو دستگاه حدود ۱٫۴ ثانیه اختلاف داشت؛ delta مطلق ingress شامل clock skew است. دامنهٔ delta از حداقل تا p95 حدود ۶٫۶ ثانیه و تا حداکثر حدود ۶۰ ثانیه بود؛ با تأخیر ورودی پیش از ASGI سازگار است. علت دقیق شبکه/صف proxy/محدودیت IP هنوز جدا نشده است.

دیتابیس پس از توقف: پرسشنامه ۶۰۰ تکمیل/۱۵۰۰۰ ردیف؛ DD تعداد ۵۷۹ run تکمیل، ۱۷۸۳۰ ردیف و ۵۸۴ run با ۳۰ ردیف؛ workflow مرحلهٔ DD برای ۵۷۶ نفر completed بود. UT تعداد ۵۶۷ run، صفر completed و ۳۶۹۵ ردیف داشت. تفاوت status اجرای DD و workflow باید مستقل گزارش شود؛ این cohort کامل نیست.

مستند رسمی LiteSpeed برای DynReqPerSec و MaxConnPerClient تنظیم سطح virtual host را توصیف می‌کند؛ افزودن آن‌ها به .htaccess به‌عنوان راه‌حل قطعی مجاز/پشتیبانی‌شده فرض نشده است. کنترل‌های امنیتی خاموش نشده‌اند. آزمون از داخل همان هاست از HTTPS عمومی، برای جداسازی مسیر بیرونی آماده شده است؛ generator در این روش منابع همان حساب را مصرف می‌کند و جایگزین آزمون اینترنتی یا ۶۰۰ مرورگر نیست.

## اینترنت اجرای اصلی

کاربر تأیید کرد هر شرکت‌کننده از اینترنت شخصی خود استفاده می‌کند. بنابراین آزمون تک‌IP با ۶۰۰ اتصال، شبیه‌سازی کامل توزیع IPهای اجرای اصلی نیست؛ نتیجهٔ آن باید از ظرفیت کل backend و محدودیت هر IP جدا شود. ۲۱ فرایند lswsgi مربوط به Staging قدیمی، با تطبیق UID/cwd/name/start-time و SIGTERM متوقف شدند؛ Uvicorn و health عمومی سالم ماندند. فایل‌های Production تغییر نکردند؛ پس از timeout مستقل اصلی، فقط یک restart معمول Passenger انجام و شش probe سالم ثبت شد.

بررسی fault-injection صف‌های واقعی JavaScript در Node مجدداً برای پرسشنامه، DD، زمان‌سنجی و Ultimatum موفق بود. این بررسی مرورگر واقعی محسوب نمی‌شود و UI تغییری نکرده است.

## آزمون ۶۰۰ نفر از داخل هاست، HTTPS عمومی

همان workflow از HTTPS عمومی Staging و LiteSpeed proxy، با k6 v2.3.0 رسمی Linux، اجرا شد؛ loopback مستقیم دور زده نشد. همهٔ ۶۰۰ سناریو کامل، صفر شکست از ۵۸۰۵۴ درخواست، p95 برابر ۲۸۷٫۵۶ms و p99 برابر ۳۹۵٫۶۸ms، exit صفر و همهٔ thresholdها موفق بودند. شمارش PostgreSQL برای ۶۰۰/۶۰۰ نفر ۱۵۰۰۰ پاسخ پرسشنامه، ۱۸۰۰۰ DD و ۱۳۲۰۰ دور UT بود؛ همهٔ runها و workflowها completed و ردیف هر run دقیق بود.

generator داخل همان حساب، حداکثر ۹۳۷٫۴۲MB RSS و هشت thread داشت؛ این بار اضافی در مقایسهٔ زمان‌ها باید لحاظ شود. ۸۰ probe اصلی بدون شکست بود. این نتیجه ظرفیت مسیر برنامه و proxy از این مبدأ را تأیید می‌کند، نه شبکهٔ اینترنت و ۶۰۰ IP/مرورگر واقعی. build سیستم Mac نیز Go/build متفاوت داشت و تفاوت مبدأ تنها متغیر کنترل‌شدهٔ کامل محسوب نمی‌شود.

برای آزمون دو مبدأ، cohort تازهٔ ۶۰۰ نفر به ۲۰۰ نفر Mac و ۴۰۰ نفر داخل هاست تقسیم شد؛ در هر بخش Frame/Control برابرند. توکن‌های بخش Mac فقط پس از تأیید صریح کاربر به پوشهٔ خصوصی همان Mac منتقل شدند. هیچ دادهٔ شرکت‌کنندهٔ واقعی در این fixture وجود ندارد و fixture وارد GitHub نمی‌شود. نتیجهٔ این آزمون در بخش بعد ثبت شده است.

## آزمون هم‌زمان دو مبدأ و نتیجهٔ نهایی ظرفیت

cohort تازهٔ ۶۰۰نفره، با ۳۰۰ Frame و ۳۰۰ Control، میان Mac (۲۰۰ نفر) و generator داخل هاست (۴۰۰ نفر) تقسیم شد. هر بخش شرط‌ها را برابر داشت. هر دو از HTTPS عمومی Staging و همان proxy استفاده کردند؛ شروع‌ها با فاصلهٔ چند ثانیه بودند و سپس ramp هم‌پوشان به مجموع ۶۰۰ VU رسید. generator داخل هاست همچنان بخشی از منابع همین حساب را مصرف می‌کرد؛ این آزمون دو IP/مبدأ دارد و معادل ۶۰۰ شبکهٔ اینترنتی نیست.

دیتابیس برای هر ۶۰۰ نفر: ۲۵ پاسخ پرسشنامه (۱۵۰۰۰)، ۳۰ DD (۱۸۰۰۰)، ۲۲ UT (۱۳۲۰۰) و سه مرحله و سه run completed؛ همه دقیق. guard بیرونی ۳۸ probe بدون شکست داشت؛ guard داخل هاست جدا ثبت شده است. p95 زمان header برنامه در Mac حدود ۱۳۹٫۶ms و p95 انتظار خارج برنامه حدود ۱۱۷۷٫۵ms بود. یک پاسخ بیرونی تا حدود ۳۷٫۹s طول کشید؛ نبود خطای HTTP به معنی نبود تأخیر محسوس نیست.

نتیجه: پشتهٔ Python/FastAPI با native ASGI و سهم منابع فعلی توان اجرای ۶۰۰ جریان کامل API را در این سناریو نشان داد. برای بازنویسی به Node.js یا خرید RAM/CPU شواهد کافی نداریم. در عین حال سرعت همهٔ مسیرهای اینترنتی و اجرای ۶۰۰ مرورگر واقعی تأیید نشده است. اختلاف مبدأ و build ابزار، اشتراک منابع generator و ساعت‌ها، تعداد محدود مبدأها و محدودیت دقیق ناشناختهٔ میزبان باید در هر تفسیر حفظ شوند.

## اقدام عملی و انتشار بعدی

1. Staging روی همین نسخهٔ تست‌شده با دو Uvicorn worker، سقف thread هشت و pool چهار باقی بماند؛ کد شروع‌های هم‌زمان و outboxهای PR #25 حفظ شوند.
2. در تست بعدی، IPهای متعددِ بیرونی و شبکهٔ نمایندهٔ شرکت‌کنندگان به کار روند؛ ظرفیت کل با سقف هر IP اشتباه نشود. هدف latency باید در همان مسیر واقعی سنجیده شود.
3. برای timeoutهای پیش از ASGI، بازهٔ زمانی، trace و summary به بررسی proxy/TLS/per-IP/WAF و مسیر شبکه داده شود. پیکربندی مدیریتی خوانده نشده و کنترل امنیتی خاموش نشده است؛ متن بررسی در سند ingress آماده است و به پشتیبانی ارسال نشده است.
4. پیش از Production، پایلوت مرورگر با قطع/وصل شبکه و بررسی export/scoring روی همین کد انجام شود؛ سپس SHA نهایی/CI، backup و روش restart native جدا بررسی شوند. 

شواهد عمومی‌شدنی در `artifacts/capacity-fix-20261103/`، ابزارها در `ops/` و CI در PR #27 ثبت می‌شوند. دعوت‌نامه‌ها، envها، کلیدها و payload شرکت‌کنندگان در مخزن قرار ندارند.

## پایان عملیات

تمام generatorها و monitorهای موقت پایان یافتند. ۱۹۰۱ تخصیص مصنوعی همین نوبت با scope دقیق مطالعهٔ Staging غیرفعال شدند؛ داده و ردیف‌ها حذف نشدند. در سه probe پایانی از داخل هاست، Staging و Production هر دو ۲۰۰ و اتصال دیتابیس سالم داشتند. hash backend و HTML هر دو محیط و request_metrics.py Staging تأیید شد. Supervisor برای Staging RUNNING باقی ماند. سلامت پایانی موفق، مشکل متناوب تاریخی Production را به‌تنهایی حل‌شده ثابت نمی‌کند؛ بازهٔ آزمون دو مبدأ از هر دو سمت guard سالم داشت.

روش استقرار، rollback اصلاح‌شده، dependency جدید، فایل‌های hash-pinned و ابزارهای تشخیص در همین PR ثبت شده‌اند. Runtime همچنان نسخهٔ تست‌شدهٔ 7af1838 است؛ commitهای گزارش/ابزار پس از آن بدون تغییر سورس برنامه، انتشار جدید runtime محسوب نمی‌شوند.
