# BarSan Experiment — سامانهٔ آزمایش آنلاین

این مخزن برنامهٔ پژوهشی ماژولار بارسان را پیاده‌سازی می‌کند: یک برنامهٔ Python/FastAPI و یک دیتابیس PostgreSQL با سه ماژول مستقل:

1. پرسشنامه
2. تسک DD در برابر Life-Trade (کد فعلی)
3. بازی اولتیماتوم

## راهنمای ضروری برای توسعه و کار با هوش مصنوعی

این مخزن برای عامل‌های هوش مصنوعی یک راهنمای اجرایی مستقل دارد. پیش از هر تغییر یا عملیات استقرار، اسناد زیر را به ترتیب بخوانید:

1. [`AGENTS.md`](AGENTS.md): دستورالعمل اجباری توسعه، تست، امنیت و استقرار برای تمام عامل‌ها.
2. [راهنمای جامع انتقال دانش و عملیات](docs/AI_HANDOFF_FA.md): معماری واقعی پروژه، مسیر فعال Passenger، محیط اجرا، دیتابیس، CI، استقرار، خطاهای قبلی و چک‌لیست تحویل.
3. [معماری جریان آزمایش](EXPERIMENT_ARCHITECTURE.md) و [معماری دیتابیس](DATABASE_ARCHITECTURE.md): مرجع منطق پژوهش و ساختار داده.

**نکتهٔ حیاتی cPanel:** Application Root برابر `/home/myexperi/lifetrade` است، اما فایل `passenger_wsgi.py` کد فعال را از `/home/myexperi/lifetrade/repo` import می‌کند. بنابراین فایل‌های runtime باید در `/home/myexperi/lifetrade/repo/` منتشر شوند، نه در ریشهٔ Application Root. جزئیات و شواهد در راهنمای انتقال دانش ثبت شده‌اند.

## آمادگی اجرا با هم‌زمانی بالا

بهینه‌سازی queryها در سه پاس انجام شده است: بررسی consent، run فعال و trial در resolve/events در یک read ترکیبی؛ حذف readهای تکراری در شروع مرحله و ذخیرهٔ پرسشنامه؛ و استفاده از aggregate و projection محدود در Ultimatum prepare برای جلوگیری از خواندن payload و تمام ردیف‌های قبلی در هر دور. تست‌ها حفظ رفتار خطا و idempotency را پوشش می‌دهند.

سه پاس بهینه‌سازی Backend و ابزارهای staging-only بار و تشخیص منابع اضافه شده‌اند. CI روی commit `c94e6590e17f552983ecbe7feea2f4abdf30be6d` با ۶۱ تست SQLite و PostgreSQL smoke/concurrency برای ۲۴ شرکت‌کننده موفق شده است. آزمون ramp-up واقعی ۶۰۰ VU روی staging در ۲ نوامبر ۲۰۲۶ اجرا شد، اما با اشباع هر ۸ پردازش LSAPI و خطاهای 503/timeout شکست خورد؛ ظرفیت ۶۰۰ نفر تأیید نشده است. جزئیات اجرا و برنامهٔ اصلاح در گزارش کارایی ثبت شده است.

ممیزی ظرفیت، مسیرهای پرتکرار، pool دیتابیس، queryها و آزمون بار ۶۰۰ شرکت‌کننده در [گزارش کارایی و آزمون بار](docs/PERFORMANCE_AND_LOAD_TESTING_FA.md) ثبت می‌شود. این گزارش محدودیت‌های واقعی cPanel/Passenger و PostgreSQL را از بهینه‌سازی‌های کد جدا می‌کند؛ موفقیت تست CI به‌تنهایی اثبات ظرفیت ۶۰۰ اتصال هم‌زمان نیست.


### کاهش درخواست‌های تکراری پرسشنامه

مسیر ذخیرهٔ هر پاسخ پرسشنامه خودش پاسخ نرمال‌شده و draft سروری را به‌روزرسانی می‌کند. بنابراین در حرکت رو به جلو، فرستادن درخواست جداگانهٔ `/api/experiment/stages/draft` تکراری است. رابط شرکت‌کننده فقط برای حرکت به سؤال قبلی، موقعیت draft را جداگانه ذخیره می‌کند؛ در workflowهای سفارشی نیز endpoint ذخیرهٔ پاسخ، draft همان مرحله را به‌روزرسانی می‌کند. پس از refresh، آخرین سؤال پاسخ‌داده‌شده ممکن است دوباره نمایش داده شود، اما پاسخ ثبت‌شده حفظ می‌شود. تعداد سؤال‌ها، ترتیب، اعتبارسنجی و شرط تکمیل تغییری نمی‌کند.

## ابزار آزمون بار در staging

برای دیدن محدودیت‌های cPanel و PostgreSQL، ابزار read-only `tests/load/host_diagnostics.py` را بررسی کنید. برای ساخت ۶۰۰ لینک آزمایشی و اجرای workflow کامل از k6، دستورالعمل `tests/load/README_FA.md` را بخوانید. این ابزار staging-only است، برای دیتابیس مستقل طراحی شده و فایل حاوی invitation tokenها را فقط به‌صورت محلی نگه می‌دارد. اجرای آن روی دامنهٔ production ممنوع است.

## وضعیت فعلی

- زیرساخت بک‌اند برای تخصیص ثابت هر شرکت‌کننده به شرط آزمایشی، لینک اختصاصی، مشاهدهٔ پیشرفت مراحل، ذخیرهٔ پیش‌نویس پرسشنامه و شروع مجدد تلاش ناقص دو تسک پیاده‌سازی شده است.
- آزمون‌های SQLite و PostgreSQL برای پایهٔ جدید و رفتارهای اصلی آن در GitHub Actions اجرا می‌شوند.
- رابط فعلی شامل صفحهٔ خوش‌آمدگویی، توضیحات و رضایت، و پرسشنامهٔ ۲۵ سؤالی با یک سؤال در هر صفحه است. رضایت، کد شرکت‌کننده و لینک اختصاصی پیش از دسترسی به مرحله‌ها در سمت سرور اعتبارسنجی می‌شوند.
- مسیر پرسشنامه و ماژول فعلی DD/Life-Trade به جریان مشترک متصل شده است. پاسخ‌های پرسشنامه براساس کد داخلی هر سؤال ذخیره می‌شوند؛ کدها در رابط شرکت‌کننده نمایش داده نمی‌شوند.
- پنل مدیریت پژوهش در مسیرهای `/admin` و `/admin/links` شامل ساخت لینک تکی/گروهی با CSV، پایش پیشرفت، خروجی سه ماژول، خروجی ZIP کامل، ساخت لینک تست کامل و لینک تست مستقل هر ماژول است.
- پاک‌سازی داده‌ها به محدودهٔ اصلی یا تست محدود شده و فقط پس از پیش‌نمایش و واردکردن عبارت تأیید دقیق انجام می‌شود؛ جدول کدهای شرکت‌کننده و تعریف ابزارها حذف نمی‌شوند.
- ارسال‌های Ultimatum تکرارپذیر شده‌اند و خطای ثبت زمان‌های کمکی دیگر مانع ادامهٔ شرکت‌کننده نمی‌شود. این نسخه همچنان باید روی cPanel/PostgreSQL پایلوت شود؛ الگوریتم پاسخ هوش مصنوعی، پروتکل اخلاق و تنظیمات واقعی میزبانی باید پیش از جمع‌آوری نهایی بررسی شوند.

معماری کامل جریان در [EXPERIMENT_ARCHITECTURE.md](EXPERIMENT_ARCHITECTURE.md) و ساختار داده در [DATABASE_ARCHITECTURE.md](DATABASE_ARCHITECTURE.md) ثبت شده است.

## رفتار بازگشت شرکت‌کننده

- شناسهٔ شرط به‌صورت پیشینی به فرد تخصیص داده می‌شود. لینک اختصاصی به‌همراه کد شرکت‌کننده اعتبارسنجی می‌شود و شرط از دیتابیس خوانده می‌شود؛ پارامتر URL منبع معتبر تعیین شرط نیست.
- پذیرش توضیحات پژوهش با نسخهٔ متن و زمان ثبت در سرور نگهداری می‌شود؛ endpointهای هویت و ماژول‌ها بدون ثبت رضایت فعال نیستند.
- پاسخ‌های پرسشنامه در سمت سرور و با شناسهٔ داخلی هر سؤال نگه داشته می‌شوند و با ورود مجدد بازیابی خواهند شد.
- اگر فرد وسط DD/Life-Trade یا اولتیماتوم خارج شود، تلاش قبلی با وضعیت `superseded` علامت می‌خورد و شروع بعدی یک تلاش تازه می‌سازد.
- دادهٔ تلاش قدیمی برای ممیزی در دیتابیس می‌ماند، ولی از خروجی اصلی CSV مربوط به Life-Trade کنار گذاشته می‌شود.
- تکمیل مرحله در سمت سرور ثبت می‌شود؛ مرحلهٔ تکمیل‌شده نباید دوباره اجرا شود.

## اجرای محلی

ماژول اصلی برنامه در فایل `barsan_experiment.py` قرار دارد. `main.py` به‌عنوان ورودی سازگاری برای تنظیمات قدیمی cPanel نگه داشته شده است.

1. Python 3.11+ نصب کنید.
2. `pip install -r requirements.txt`
3. یک توکن مدیریتی تنظیم کنید: `export ADMIN_TOKEN='یک-رمز-طولانی'`
4. `uvicorn barsan_experiment:app --reload`
5. مرورگر: `http://127.0.0.1:8000`
6. سلامت API: `http://127.0.0.1:8000/api/health`

بدون `DATABASE_URL` از SQLite محلی استفاده می‌شود. در production از PostgreSQL استفاده کنید؛ دیسک محلی بسیاری از هاست‌های موقت پایدار نیست.

## پنل مدیریت آزمایش

پس از استقرار، پنل در `/admin` و `/admin/links` در دسترس است. همهٔ عملیات آن با هدر `X-Admin-Token` محافظت می‌شوند. توکن فقط در حافظهٔ صفحه می‌ماند و در localStorage ذخیره نمی‌شود.

### ساخت لینک‌ها

در صفحه می‌توان یک کد یا فهرستی از کدها را وارد کرد؛ هر خط `CODE`، `CODE,Frame` یا `CODE,Control` است. فایل CSV نیز با ستون‌های `participant_code` یا `code` و `group` یا `condition_code` پذیرفته می‌شود. نگاشت گروه‌ها `Frame → A` و `Control → B` است.

در همان بخش، مدیریت لینک‌ها تعداد لینک‌های فعال/غیرفعال را نشان می‌دهد و فیلتر وضعیت، جست‌وجو، فعال‌سازی/غیرفعال‌سازی گروهی، حذف همهٔ لینک‌های غیرفعال و خروجی CSV از لینک‌های فعال دارد. حذف لینک غیرفعال تخصیص لینک و رضایت وابسته به آن را حذف می‌کند، ولی داده‌های پاسخ/اجرای پژوهشی را پاک نمی‌کند. برای صدور مجدد لینک قدیمی، توکن قبلی باطل می‌شود و URL جدید جایگزین می‌گردد.

از این نسخه، توکن خام همچنان به‌صورت هش برای اعتبارسنجی نگه داشته می‌شود و نسخهٔ قابل بازیابی آن با Fernet رمزنگاری‌شده ذخیره می‌شود تا CSV لینک‌های جدید قابل استفاده باشد. کلید رمزنگاری به‌طور پیش‌فرض در فایل خصوصی `.barsan_invitation_tokens.key` در پوشهٔ خانگی حساب cPanel و بیرون از ریشهٔ وب نگه‌داری می‌شود؛ مجوز آن محدود است. این فایل را در backup امن همراه با دیتابیس نگه دارید و هرگز وارد GitHub نکنید. لینک‌هایی که پیش از این تغییر ساخته شده‌اند، فقط هش توکن را دارند و URL آن‌ها قابل بازیابی نیست؛ برای این موارد از گزینهٔ «صدور URL جدید» استفاده کنید، با این آگاهی که لینک قبلی دیگر کار نخواهد کرد.

### تست کامل و تست مستقل ماژول

- «ساخت دو لینک تست» یک زوج لینک می‌سازد: Frame و Control؛ کد ورود هر دو `TEST` است.
- برای تست جداگانهٔ پرسشنامه، DD/Life-Trade یا Ultimatum از «تست مستقل ماژول‌ها» استفاده کنید. لینک فقط همان ماژول را اجرا می‌کند. مراحل پیشین لازم برای مسیریابی در مطالعهٔ تست به‌صورت synthetic تکمیل‌شده علامت می‌خورند و پرچم `test_prerequisite` دارند؛ این ردیف‌ها دادهٔ رفتاری واقعی محسوب نمی‌شوند.
- هر نسل لینک تست `study_code` جداگانه دارد و با پیشوند `barsan-test-` ذخیره می‌شود. همهٔ نسل‌ها در خروجی تست هستند؛ هیچ‌کدام در خروجی اصلی وارد نمی‌شوند.

### پایش و خروجی‌ها

`GET /api/admin/progress?scope=main|test` وضعیت هر فرد را با مرحلهٔ فعلی، وضعیت سه ماژول و آخرین زمان فعالیت می‌دهد. `stale_incomplete` یعنی از آخرین فعالیت بیش از ۲۴ ساعت گذشته است؛ این برچسب شاخص پیگیری است، نه اثبات قطعی ترک آزمایش.

- `GET /api/admin/export.csv?scope=test`: خروجی Life-Trade تست
- `GET /api/admin/questionnaire/export.csv?scope=test`: خروجی پرسشنامهٔ تست
- `GET /api/admin/ultimatum/export.csv?scope=test`: خروجی Ultimatum تست
- `GET /api/admin/export-all.zip?scope=main|test`: هر سه CSV به‌همراه `participant_progress.csv` در یک ZIP

بدون `scope=test` خروجی‌ها فقط مطالعهٔ اصلی را شامل می‌شوند. هر فایل دارای ستون `study_code` است.

### پاک‌سازی محدود و کنترل‌شده

`GET /api/admin/maintenance/preview?scope=main|test` قبل از پاک‌سازی، تعداد مشارکت‌ها، تخصیص‌ها، اجرای ماژول‌ها و ردیف‌های رفتاری را نشان می‌دهد.

`POST /api/admin/maintenance/reset` فقط وقتی اجرا می‌شود که `scope` و عبارت دقیق تأیید با هم مطابقت داشته باشند:
- اصلی: `{"scope":"main","confirm_phrase":"CLEAR MAIN DATA"}`
- تست: `{"scope":"test","confirm_phrase":"CLEAR TEST DATA"}`

پاک‌سازی اصلی همهٔ تخصیص‌ها، رضایت‌ها، پیشرفت‌ها، اجراها و پاسخ‌های مرتبط با `STUDY_CODE` اصلی را حذف می‌کند، بنابراین لینک‌های اصلی قبلی دیگر معتبر نیستند. پاک‌سازی تست همهٔ فضاهای `barsan-test-*` را حذف می‌کند. رکوردهای اصلی جدول `participants` و ثبت ابزارها حفظ می‌شوند. قبل از پاک‌سازی واقعی، از PostgreSQL بکاپ مستقل بگیرید؛ پنل ابزار اجرای SQL دلخواه یا جایگزین بکاپ نیست.

### تغییر نام مسیر cPanel

برای مسیر جدید از **Application root** برابر `barsan_experiment` و **Application URL** برابر `barsan-experiment` استفاده کنید. در cPanel این دو فیلد تنظیمات میزبانی‌اند و فقط تغییر کد مخزن آن‌ها را تغییر نمی‌دهد. دستورالعمل مهاجرت بدون از دست‌دادن لینک‌های قدیمی در [CPANEL_RENAME.md](CPANEL_RENAME.md) آمده است.

در production مقدار `PUBLIC_EXPERIMENT_URL` را روی URL عمومی نهایی تنظیم کنید؛ اگر تنظیم نشده باشد، برنامه مسیر نصب‌شده را از درخواست فعلی تشخیص می‌دهد. همهٔ APIهای مدیریتی با `X-Admin-Token` محافظت شده‌اند؛ توکن را در کد مرورگر، لینک شرکت‌کنندگان یا مخزن قرار ندهید.

## وضعیت و فرض‌های موقت اولتیماتوم

- چهار بلوک اصلی در هر مشارکت اجرا می‌شوند؛ ترتیب بلوک‌ها در سمت سرور تصادفی و در متادیتای اجرای همان فرد ذخیره می‌شود و هر بلوک پنج دور دارد. سرور ترتیب بلوک‌ها و دورها را کنترل می‌کند و اجازهٔ پرش از دور، جابه‌جایی بلوک یا ورود به بازی اصلی پیش از تکمیل هر دو دور تمرینی را نمی‌دهد. دو دور تمرینی در جدول ذخیره می‌شوند، ولی در امتیاز نهایی محاسبه نمی‌شوند.
- کد UI فعلاً فرض می‌کند شرط `A` به گروه Frame و شرط `B` به گروه Control نگاشت می‌شود.
- پیشنهاد هوش مصنوعی با نمونه‌گیری از نرمال گسسته و محدود به اعداد صحیح ۰ تا ۱۰، با میانگین ۵ و پارامتر انحراف معیار ۴ تولید می‌شود. به‌دلیل گسسته‌سازی و محدودسازی بازه، انحراف معیار واقعی توزیع نهایی حدود ۲٫۷۹ است؛ پاسخ دوجمله‌ای هوش مصنوعی تغییری نکرده است.
- پاسخ دودویی هوش مصنوعی فعلاً با یک صورت‌بندی موقت از توزیع دوجمله‌ای پیاده‌سازی شده: ۱۰ آزمایش برنولی با احتمال `p = سهم پیشنهادی به هوش مصنوعی / 10` و قبول در صورت نمونهٔ حداقل ۵. این پارامترها باید با پژوهشگر نهایی شوند.
- در شرط «همکار»، UI همکار حاضر در سالن را نمایش می‌دهد، اما تصمیم‌ها همچنان در سمت سرور و توسط الگوریتم تولید می‌شوند؛ این دستکاری باید با طرح اخلاق پژوهش و هرگونه debriefing مصوب سازگار باشد.
- دو دور تمرینی مجزا فعلاً در نظر گرفته شده است تا شرکت‌کننده هر دو نقش پیشنهاددهنده و پاسخ‌دهنده را تجربه کند؛ اگر منظور پروتکل یک دور تمرینی واحد بوده، این تصمیم باید اصلاح شود.

## محدودیت RT

RT با `performance.now()` از زمان بلافاصله پس از ساخت عناصر محرک اندازه‌گیری می‌شود؛ این معادل دقیق همگام‌سازی فریم PsychoPy نیست. دستگاه، مرورگر، نرخ تازه‌سازی و لمس می‌توانند روی RT اثر بگذارند. این تفاوت باید در گزارش پژوهشی ذکر شود و پایلوت انجام شود.

## حریم خصوصی و امنیت

شناسهٔ پژوهشی به‌تنهایی ناشناس‌بودن مطلق را تضمین نمی‌کند. متادیتای دستگاه فعلاً در اجرای قدیمی Life-Trade شامل user-agent و اندازهٔ صفحه است. توکن خام لینک در دیتابیس به‌صورت متن آشکار ذخیره نمی‌شود: هش SHA-256 برای اعتبارسنجی و نسخهٔ Fernet رمزنگاری‌شده برای قابلیت خروجی گرفتن از URL نگه‌داری می‌شود. کلید رمزنگاری فایل خصوصی `.barsan_invitation_tokens.key` در پوشهٔ خانگی حساب cPanel است و باید همراه بکاپ دیتابیس به‌صورت امن نگه‌داری شود؛ گم‌شدن کلید، URLهای ذخیره‌شدهٔ رمزنگاری‌شده را غیرقابل بازیابی می‌کند. لینک‌های قدیمی که ciphertext ندارند باید به‌صورت آگاهانه دوباره صادر شوند. نسخهٔ رضایت و زمان پذیرش ثبت می‌شوند؛ IP یا اطلاعات هویتی اضافه برای ثبت رضایت گردآوری نمی‌شود. `ADMIN_TOKEN` و `DATABASE_URL` محرمانه‌اند و نباید وارد GitHub شوند.

## وضعیت به‌روزشدهٔ رابط شرکت‌کننده — ۳۱ اکتبر ۲۰۲۶

این بخش وضعیت قطعی متن و نمایش بازی باشگاه رانندگان را ثبت می‌کند. عنوان‌ها و توضیحات داخلی کد می‌توانند نام فنی ماژول یا بلوک را داشته باشند، اما این اصطلاحات نباید به رابط شرکت‌کننده نشت کنند.

### صفحهٔ خوش‌آمدگویی و رضایت

- صفحهٔ خوش‌آمدگویی عنوان «به برنامهٔ پژوهشی بارسان خوش آمدید»، فهرست شماره‌دار مراحل همان شرکت‌کننده و دکمهٔ «ادامه» را نمایش می‌دهد؛ پاراگراف توضیحی اضافه دربارهٔ ترتیب یا تعداد مرحله‌ها نمایش داده نمی‌شود.
- مراحل با درخواست عمومی `GET /api/experiment/workflow?invite=...` و براساس workflow واقعی لینک خوانده می‌شوند؛ Frontend نباید ترتیب را با یک فهرست ثابت جایگزین کند.
- عنوان‌های participant-facing: `questionnaire` → «پرسشنامه»، `dd_lifetrade` → «بازی انتخاب»، و `ultimatum` / `ultimatum_frame` / `ultimatum_control` → «بازی باشگاه رانندگان بارسان».
- نام‌های فنی انگلیسی، کد ماژول‌ها، Frame/Control و descriptionهای داخلی API در فهرست خوش‌آمدگویی نمایش داده نمی‌شوند. توضیح اضافی زیر نام هیچ مرحله‌ای وجود ندارد.
- در workflow پیش‌فرض قدیمی، endpoint عمومی دو مرحلهٔ پرسشنامه و بازی انتخاب را می‌دهد؛ چون جریان قدیمی پس از DD/Life-Trade به Ultimatum می‌رود، مرحلهٔ بازی باشگاه رانندگان بارسان نیز در انتهای فهرست اضافه می‌شود. در workflow سفارشی، فقط همان مراحل پیکربندی‌شده نشان داده می‌شوند؛ لینک تست مستقل فقط همان ماژول را نشان می‌دهد.
- پاراگراف درخواست‌شده دربارهٔ وارد نکردن نام، نام خانوادگی، شمارهٔ ملی و شمارهٔ تلفن از صفحهٔ رضایت حذف شده است. این تغییر به معنی حذف سایر توضیحات رضایت نیست.
- متن راهنمای پرسشنامه دربارهٔ پاسخ ندادن با اطلاعات هویتی، در صورت وجود در همان ماژول، محتوایی جدا از پاراگراف حذف‌شدهٔ صفحهٔ رضایت است و نباید بدون درخواست مستقل حذف شود.

### متن و طراحی بازی

- معرفی بازی با عبارت «شما در این بازی برای کسب امتیاز باشگاه رانندگان با یک بازیکن دیگر بازی می‌کنید.» آغاز می‌شود.
- نام نقش‌ها در رابط به شکل «پیشنهاد دهنده» و «پاسخ دهنده» نوشته می‌شوند.
- توضیح تمرین: «قبل از شروع بازی اصلی، دو دور تمرینی اجرا می‌شود اما امتیازها و داده‌های این دو دور در امتیاز نهایی و برنامه پژوهشی لحاظ نمی‌شوند.»
- گذار از تمرین به بازی اصلی: «دور‌های تمرینی به پایان رسید. الان بازی اصلی شروع می‌شود.»
- متن صفحهٔ معرفی و تیترها، توضیحات، نقش‌ها، نتیجه‌ها و عددهای امتیاز در صفحات پویا باید افقی وسط‌چین باشند. عنوان و متن اصلی هر صفحهٔ راهنما نیز باید در مرکز عمودی کارت قرار گیرد؛ نوار پیشرفت و topbar می‌توانند بالا و دکمه‌ها پایین بمانند.
- در پرسشنامه، عنوان دستور و عبارت سؤال در گروه میانی کارت باشند؛ در Ultimatum، عنوان و محتوای اصلی در ناحیهٔ میانی زیر topbar قرار بگیرند. در موبایل محتوا نباید از بالا بریده شود و بخش‌های بلند باید قابل scroll بمانند.
- عنوان هر دو تسک KT/DD و LT در دستورالعمل شرکت‌کننده «بازی انتخاب» است؛ نام‌های فنی «5-Trial DD Task» و «Life-Trade Reward» برای شرکت‌کننده نمایش داده نمی‌شوند. عنوان Ultimatum «بازی باشگاه رانندگان بارسان» است.
- اعداد امتیاز در پیشنهاد، نتیجهٔ دور و خلاصهٔ پنج دور باید درشت و خوانا باشند.
- در پایان هر مجموعهٔ پنج‌دوری فقط عنوان «در ۵ دور قبلی شما:» و دو شاخص «امتیاز به دست آوردید» و «امتیاز از دست دادید» نمایش داده می‌شوند. هر دو شاخص باید همیشه حاضر باشند؛ نمایش امتیاز ازدست‌رفته به شرط Frame یا Control وابسته نیست.
- نوار امتیاز تجمیعی اضافی از صفحهٔ خلاصهٔ پنج‌دوری حذف شده تا صفحه فقط عنوان خلاصه و دو باکس امتیاز را نشان دهد.
- دکمهٔ گذار بین مجموعه‌ها «دور بعدی» است. عبارت‌های ساختاری مانند «شروع بخش بازی»، «پایان این بخش» و «پایان این بلوک» در متن قابل مشاهدهٔ شرکت‌کننده مجاز نیستند.
- صفحهٔ امتیاز نهایی فقط یک عنوان «امتیاز نهایی» دارد. باکس امتیاز و عدد آن از خلاصه‌های معمول بزرگ‌تر است و برچسب خالی تکراری برای کارت عدد ساخته نمی‌شود.
- پیام پایان مطالعه باید شامل این متن باشد: «بارسانی عزیز، بازی و برنامه ‌پژوهشی به پایان رسید. امتیاز شما از طریق کد یکتای شما به حساب کاربری‌تان در باشگاه رانندگان بارسان منتقل خواهد شد.»

### آزمون رگرسیون رابط شرکت‌کننده

فایل `tests/test_participant_ui.py` متن‌ها و ساختارهای حساس بالا را با جداسازی بخش HTML خوش‌آمدگویی و توابع رندر خلاصه/نتیجه بررسی می‌کند؛ از جمله نبود پاراگراف حذف‌شده، املای نقش‌ها، متن تمرین، خلاصهٔ پنج‌دوری، نبود تیترهای بخش‌بندی، وسط‌چین بودن و یکتایی عنوان امتیاز نهایی. این تست در اجرای عادی `pytest -q` اجرا می‌شود.

## استقرار روی هاست cPanel / Passenger

### مشخصات محیط فعلی

| مورد | مقدار شناخته‌شده |
|---|---|
| نوع میزبانی | هاست اشتراکی cPanel |
| اجرای Python | Setup Python App با Passenger |
| Framework | FastAPI |
| URL عمومی | `https://my-experiment.ir/lifetrade/` |
| Prefix برنامه | `/lifetrade` |
| Application root | `/home/myexperi/lifetrade` |
| کلون Git | `/home/myexperi/lifetrade/repo` |
| فایل HTML منتشرشده | `/home/myexperi/lifetrade/repo/app/index.html` |
| درخواست Restart Passenger | `/home/myexperi/lifetrade/tmp/restart.txt` |
| فایل کلید SSH برای Deploy | `/home/myexperi/.ssh/lifetrade_deploy` |
| نام دیتابیس PostgreSQL | `myexperi_lifetrade_study` |

کلید خصوصی SSH، رمز دیتابیس، مقدار `DATABASE_URL` و مقدار `ADMIN_TOKEN` محرمانه‌اند. مقدار secret نباید درخواست، نمایش، چاپ، در README یا در Git ثبت شود. مسیر فایل کلید برای اجرای دستور deploy ثبت شده است؛ خود محتوای کلید نباید خوانده یا منتقل شود.

**تنظیم Passenger را حدس نزنید:** فایل Startup و Entry point فعال را در **Setup Python App** بررسی کنید. وجود `main.py` به‌تنهایی اثبات نمی‌کند که cPanel آن را اجرا می‌کند؛ این فایل برای سازگاری با هدف قدیمی `main:app` حفظ شده است.

### متغیرهای محیطی

| متغیر | نقش |
|---|---|
| `DATABASE_URL` | connection string کامل PostgreSQL؛ فقط از Environment Variables در cPanel خوانده شود |
| `ADMIN_TOKEN` | توکن محافظت از APIهای مدیریتی؛ secret |
| `STUDY_CODE` | کد مطالعه؛ مقدار پیش‌فرض `main-study` |
| `PUBLIC_EXPERIMENT_URL` | آدرس عمومی؛ پیش‌فرض کد `https://my-experiment.ir/lifetrade` است. طبق اطلاعات ثبت‌شده، مقدار زندهٔ این متغیر در هاست خالی نیست و نباید بدون مشاهدهٔ شواهد، مشکل به خالی بودن آن نسبت داده شود |
| `DB_POOL_MIN_SIZE`, `DB_POOL_MAX_SIZE` | اندازهٔ حداقل/حداکثر pool؛ اختیاری با پیش‌فرض کد |
| `DB_POOL_TIMEOUT`, `DB_POOL_MAX_WAITING` | timeout و صف انتظار pool؛ اختیاری با پیش‌فرض کد |
| `SQLITE_BUSY_TIMEOUT_MS` | timeout قفل SQLite؛ اختیاری |
| `DB_CONNECT_TIMEOUT` | timeout اتصال دیتابیس؛ اختیاری |

نام `myexperi_lifetrade_study` نام دیتابیس است، نه لزوماً مقدار کامل `DATABASE_URL`. آدرس میزبان، username، port و رمز اتصال را از پیکربندی cPanel بخوانید و حدس نزنید.

### قاعدهٔ انتشار UI-only

در تغییرات صرفاً ظاهری، فایل‌های Backend و دیتابیس نباید لمس شوند. روال انتشار:

1. از کلون مخزن و فایل HTML زنده بکاپ بگیرید.
2. remote مخزن را روی `git@github.com:Rezaaoow/barsan-experiment.git` تنظیم کنید.
3. ref مربوط به PR یا شاخه را fetch کنید.
4. SHA commit را با SHA دقیق همان نسخهٔ تأییدشده در CI مقایسه کنید.
5. فقط `app/index.html` را از commit تأییدشده استخراج کنید و به `/home/myexperi/lifetrade/repo/app/index.html` منتقل کنید. این مسیر در کلون فعال Passenger است؛ مسیر هم‌نام زیر `/home/myexperi/lifetrade/app/` غیرفعال است.
6. `touch /home/myexperi/lifetrade/tmp/restart.txt` را اجرا کنید.
7. HTML زنده را با query string یکتا دریافت و نشانگر نسخه را بررسی کنید. در صورت شکست verify، فایل قبلی را از backup برگردانید و Passenger را دوباره restart کنید.

در انتشار UI-only از `git reset --hard` استفاده نکنید و هیچ migration، reset یا عملیات پاک‌سازی دیتابیس اجرا نکنید. دستور deploy اختصاصی باید به SHA دقیق CI قفل شود؛ PR یا branch متحرک بدون تطبیق SHA نباید منتشر شود.

### انتشار Backend

اگر کد Backend تغییر کند، فقط در صورت نیاز فایل‌های `barsan_experiment.py`، `main.py`، `app.py` و `requirements.txt` را نیز در کلون فعال Passenger یعنی `/home/myexperi/lifetrade/repo/` منتشر کنید؛ این bootstrap کد را از همان مسیر import می‌کند. اگر وابستگی‌ها تغییر کردند، virtualenv متصل به همان Python App را به‌روزرسانی کنید. قبل از هر تغییر Backend، تنظیم Startup/Entry point و متغیرهای محیطی زنده را در cPanel بررسی کنید. تغییر Backend نباید موجب تغییر یا reset دیتابیس شود مگر migration جداگانه، پشتیبان مستقل و تأیید صریح وجود داشته باشد.

## قاعدهٔ اجباری مستندسازی پیش از Commit

برای تمام درخواست‌های بعدی توسعهٔ این پروژه:

1. پیش از تغییر کد، شاخه و commit جاری و README را از GitHub بخوانید.
2. ابتدا README را با رفتار، متن، ساختار، API، تنظیمات یا تستی که قرار است تغییر کند به‌روزرسانی کنید.
3. سپس تغییر کد را اعمال کنید؛ README و کد باید در یک commit منسجم ثبت شوند.
4. تست مرتبط و CI همان commit را بررسی کنید.
5. پس از CI موفق، دستور انتشار را به SHA دقیق همان commit قفل کنید.
6. هیچ ادعای deploy انجام‌شده نکنید تا خروجی تأییدکننده از هاست دریافت شود.

اگر تغییر فقط UI است، دستور انتشار فقط HTML را منتقل کند. اگر تغییر backend است، فایل‌های مرتبط با backend و وابستگی‌های لازم جداگانه و با پشتیبان منتشر شوند. در هیچ‌کدام از این مسیرها نباید secretها وارد Git یا خروجی Terminal شوند.
