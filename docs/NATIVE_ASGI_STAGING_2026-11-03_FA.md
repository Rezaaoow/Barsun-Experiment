# نتیجهٔ آزمون ساختار جدید روی همان هاست

> گزارش جدیدتر: [اصلاح ظرفیت و آزمون‌های کامل ۶۰۰جریانی](CAPACITY_FIX_2026-11-03_FA.md). ممیزی بعدی ۱۶ خطای ساخت thread را در log بار قبلی یافت؛ ساختار و نتایج این سند snapshot تاریخی قبل از اصلاح‌اند.


تاریخ گزارش: ۳ نوامبر ۲۰۲۶، به وقت تهران. عملیات از شب ۲ نوامبر آغاز شد؛ نام پوشه‌های عملیاتی 20261102 باقی مانده است.

## نتیجهٔ مستقیم درخواست

همین حساب cPanel امکان اجرای مستقل Uvicorn و reverse proxy روی دامنهٔ Staging را دارد. ساختار جدید واقعاً روی مسیر عمومی فعال و پس از قطع SSH نیز برقرار ماند:

```text
HTTPS staging.my-experiment.ir/lifetrade/
        → LiteSpeed HTTP reverse proxy
        → 127.0.0.1:8766
        → Uvicorn، دو worker
        → همان FastAPI و PostgreSQL Staging
```

Nginx و دسترسی root در این حساب موجود نبود؛ به‌جای نصب وب‌سرور دیگر، از proxy وب‌سرور موجود استفاده شد. این روش در [مستندات رسمی LiteSpeed](https://docs.litespeedtech.com/lsws/cp/cpanel/rewrite-proxy/) پشتیبانی می‌شود و در این هاست نیز به‌صورت عملی تأیید شد.

پلن اعلام‌شدهٔ دو هسته و چهار GB تغییر نکرد. Python، FastAPI و کد پژوهش بازنویسی نشدند. SHA همان `e2b725cd0e1924d2dfcbb16f3cbb19d59496bd64` باقی ماند. CLI و مقادیر pool دیتابیس برنامه تغییر نکردند؛ دو worker حداکثر هشت اتصال pool دارند. processهای native داخل همان cgroup/LVE حساب 1229 بودند؛ از سهم منابع حساب خارج نشدند.

پشتیبانی از ساختار جدید تأیید شد؛ **ظرفیت عمومی ۶۰۰ نفر تأیید نشد**. فرض کافی‌بودن تغییر روش اجرا به‌تنهایی، با نتایج این نوبت تأیید نشده است.

## تغییرات واقعی و وضعیت ماندگار

- Uvicorn روی loopback و پورت 8766 اجرا شد؛ هیچ listener روی 0.0.0.0 ساخته نشد. پورت 8765 از قبل اشغال بود و process آن تغییر نکرد.
- قبل از تغییر .htaccess، backup خصوصی از مسیر Staging گرفته شد. proxy جدید فقط در `/home/myexperi/public_html/staging/lifetrade/.htaccess` است.
- پاسخ عمومی health و HTML، header `X-Barsan-Runtime: uvicorn-pr25-native` داشتند. hash HTML دقیقاً با PR 25 مطابق بود.
- Supervisor 4.3.0 فقط در virtualenv Staging نصب شد؛ کنترل آن از socket خصوصی با مجوز 0600 در پوشهٔ خصوصی 0700 انجام می‌شود. سرویس دو worker پس از خروج SSH RUNNING ماند و crash یا restart ناخواسته در لاگ آن ثبت نشد.
- یک ورودی @reboot برای Supervisor همین Staging به crontab موجود افزوده شد؛ ورودی‌های دیگر حفظ و نسخهٔ قبلی خصوصی backup شد. reboot کل هاست انجام یا آزمایش نشد.
- `current-release.json` اکنون روش اجرا و روش restart جدید را ثبت می‌کند؛ دستور restart عادی Passenger، Uvicorn را reload نمی‌کند.
- ۱۹۰۱ تخصیص مصنوعی این نوبت غیرفعال شدند. داده‌ها برای ممیزی حذف نشدند. بار، تونل تشخیصی و مانیتورهای موقت بسته شدند؛ خود سرویس جدید Staging باقی ماند.
- کد و تنظیمات Production به ساختار جدید منتقل نشدند. فایل‌های آن با hash قبلی تطبیق داشتند. برای بازیابی timeout، فقط restart معمول Passenger اصلی انجام شد؛ مشکل سلامت متناوب آن کاملاً حل‌شده محسوب نمی‌شود.

## آزمون صحت عملکرد

همان بررسی هفت‌گانهٔ API از مسیر عمومی جدید موفق شد: replay شروع با شناسهٔ ثابت، حفظ اجرای superseded، batch اتمیک پرسشنامه، تشخیص تکرار رخداد زمانی، ۳۰ trial یکتای DD با ارسال تکراری، ۲۲ دور Ultimatum Frame و ۲۲ دور Control، و چهار مرحلهٔ completed. این بررسی شمارش مستقیم PostgreSQL داشت.

کد UI تغییر نکرد و HTML همان commit بود. این نوبت، تست کامل UI/مرورگر با ۶۰۰ مرورگر واقعی یا سنجش شبکهٔ سالن محسوب نمی‌شود.

آزمون ۱۰۰ نفر exit code صفر داشت و تمام thresholdهای تعریف‌شده را گذراند. این مقایسه روی همان کد و همان هاست است؛ بار زمینهٔ میزبان مشترک تحت کنترل کامل آزمایش نبود.

آزمون ۶۰۰ نفر cohort تازه، نصف Frame و نصف Control داشت؛ طی پنج مرحلهٔ ۲۰ثانیه‌ای به سطوح ۱۰۰، ۲۰۰، ۳۰۰، ۴۰۰ و ۶۰۰ رسید، سپس چهار دقیقه سطح ۶۰۰ را نگه داشت و پایین آمد. هر VU فقط یک جریان کامل اجرا می‌کرد و پس از تکمیل idle می‌شد؛ این آزمون، ۳۰ دقیقه فعالیت پیوستهٔ ۶۰۰ کاربر نیست.

از خطاهای عمومی ۶۰۰ نفر، ۴۶۴ مورد status=0 داشتند، عمدتاً timeout و تعدادی خطای انتقال مانند قطع stream؛ یک پاسخ 500 هم رخ داد. شکست‌های اصلی در انتظار پاسخ بودند، نه صرف زمان ارسال body. مدت متوسط waiting حدود ۲٫۰۶ ثانیه و p95 آن حدود ۸٫۸۶ ثانیه بود.

شمارش مستقل دیتابیس پس از پایان آزمون:

|---|---|---|
| پرسشنامه | ۱۰۰ / ۲۵۰۰ | ۶۰۰ / ۱۵۰۰۰ |
| DD | ۱۰۰ / ۳۰۰۰ | ۵۹۸ / ۱۷۹۹۵ |

اختلاف ۵۳ تکمیل k6 و ۵۵ تکمیل سمت سرور به این معنی است که شمارندهٔ driver و وضعیت server یکی نیستند؛ پاسخ ممکن است commit شده باشد ولی client مرحلهٔ بعد/ACK را به پایان نرسانده باشد. هیچ‌یک از این اعداد نباید «۶۰۰ اجرای موفق» معرفی شود. در driver، خطای heartbeat می‌تواند سناریو را متوقف کند؛ مرورگر PR 25 زمان‌سنجی را به‌صورت صف مقاوم‌تر مدیریت می‌کند، ولی خطاهای واقعی HTTP همچنان وجود دارند.

## تشخیص با مسیر خصوصی

برای تفکیک وب‌سرور از backend، تونل موقت SSH فقط روی 127.0.0.1 کامپیوتر آزمون، به پورت loopback Uvicorn ایجاد شد. این مسیر همچنان از کامپیوتر خارج از هاست بار می‌فرستاد، ولی HTTPS/proxy عمومی را دور می‌زد. این یک مسیر تشخیصی است و روش توزیع آزمایش به شرکت‌کنندگان نیست.

| اجرای خصوصی | نتیجه |
|---|---|
| اولین cohort ۶۰۰ | پس از حدود ۳۰ ثانیه به‌دلیل دو timeout متوالی health اصلی متوقف شد؛ ۶۵۵ درخواست، بدون شکست HTTP؛ هیچ جریان کاملی هنوز فرصت پایان نداشت. نتیجهٔ ظرفیت ندارد. |
| cohort تازه پس از بازیابی و پنج health سالم اصلی | ۸ تکمیل از ۶۰۰؛ ۳۴۸۵ شکست از ۳۹۴۲۹ درخواست؛ p95 حدود ۷٫۳۷s؛ ۳۴۷۰ خطای انتقال با status=0، از جمله EOF. |

در اجرای دوم، همهٔ ۶۰۰ پرسشنامه و همهٔ ۶۰۰ DD با ۱۵۰۰۰ و ۱۸۰۰۰ ردیف ثبت شدند؛ Ultimatum هشت تکمیل و ۵۸۸۳ ردیف داشت. log خود تونل پیام Too many open files یا administratively prohibited نداشت. بااین‌حال تونل یک لایهٔ انتقال اضافی است و EOFهای آن مانع از آن‌اند که این نتیجه را معیار خالص ظرفیت FastAPI یا اثبات علت تمام خطاهای عمومی بدانیم. همچنین این اجرا ثابت نمی‌کند علت فقط LiteSpeed است.

## منابع مشاهده‌شده و حدود استنتاج

در نمونه‌های پنج‌ثانیه‌ای اجرای عمومی ۶۰۰، مجموع RSS processهای native و supervisor حدود ۱۸۸MB و بیشترین CPU نمونه‌برداری‌شده حدود ۰٫۳۹ هسته بود؛ بیشترین اتصال کل PostgreSQL ۲۳ و active نمونه‌برداری‌شده یک بود. RSS جمع‌شده می‌تواند صفحات مشترک داشته باشد و این عدد مصرف کل حساب نیست.

در یک snapshot پنج‌ثانیه‌ای حین اجرای خصوصی دوم، processهای Uvicorn حدود ۱۷۱MB RSS، ۴۲ thread، ۵۴۰ descriptor و حدود ۰٫۳۱ هسته CPU داشتند؛ اتصال‌های مشاهده‌شدهٔ Staging idle بودند. monitor پیوسته پیش از پایان اجرای خصوصی دوم تمام شده بود؛ این snapshot را نباید حداکثر مصرف کل آن اجرا معرفی کرد.

در این شواهد نشانهٔ اشباع RAM یا مصرف پیوستهٔ هر دو CPU در processهای برنامه دیده نشد. اما faultهای کل LVE، سهم IO، صف ورودی، محدودیت اتصال هر IP و مدت واقعی هر handler به‌طور کامل اندازه‌گیری نشده‌اند. بنابراین نه خرید منابع بیشتر توجیه شده، نه کفایت قطعی همهٔ محدودیت‌های حساب برای ۶۰۰ نفر اثبات شده است.

## خطای نرم‌افزاری مشخص

یک traceback واقعی از برنامه ثبت شد:

```text
psycopg.errors.UniqueViolation:
duplicate key value violates unique constraint
experiment_stage_start_requests_pkey
```

مسیر: `start_experiment_stage`، درج ledger درخواست شروع، حدود خط ۲۸۴۵ در e2b725c. دو retry هم‌زمان می‌توانند هر دو پیش از درج، ledger را خالی ببینند و یکی در INSERT خطای 500 بگیرد. تست replay ترتیبی این رقابت را نمی‌سنجد.

اصلاح مشخص پیشنهادی: در PostgreSQL، شروع‌های مربوط به همان assignment در همان تراکنش با row lock سریالی شوند؛ lookup ledger بعد از گرفتن lock انجام شود. در SQLite از تراکنش write مناسب استفاده شود. سپس تست هم‌زمانی با start_request_id یکسان باید یک run و پاسخ موفقِ یکسان برای هر دو درخواست، بدون 500، تأیید کند. این اصلاح در این نوبت روی runtime اعمال نشده است؛ کد همچنان e2b725c است. این نقص، تمام هزاران خطای انتقال را توضیح نمی‌دهد.

نام metric `web_server_overloads` در driver صرفاً شمارندهٔ 5xxهایی است که متن مشخص pool را ندارند؛ نام آن منشأ خطا را اثبات نمی‌کند. پاسخ 500 بالا از خود برنامه بود. شمارندهٔ `network_timeouts` نیز همهٔ status=0ها را می‌شمارد و منحصر به timeout نیست.

## مسیر عملی بعدی

1. ساختار native روی Staging حفظ شود؛ برای تغییر زبان یا ارتقای RAM/CPU براساس این نتایج تصمیم نگیریم.
2. رقابت start_request_id با تغییر محدود و تست هم‌زمانی PostgreSQL اصلاح شود.
3. پیش از یک آزمون بزرگ دیگر، زمان شروع/پایان handler، تعداد درخواست‌های در حال اجرا، زمان انتظار pool و مدت SQL در لاگ خصوصیِ بدون token ثبت شود. زمان داخل برنامه با waiting بیرونی k6 تطبیق داده شود تا صف شبکه/پروکسی از زمان اجرای کد جدا شود.
4. از میزبان مقدار واقعی و آمار صف برای proxy به 127.0.0.1:8766، Max Connections/Max SSL Connections، محدودیت هر IP، HTTP/2 stream و faultهای LVE درخواست شود. LiteSpeed این سقف‌ها را جدا از RAM/CPU تعریف می‌کند؛ [Max Connections](https://www.litespeedtech.com/docs/webserver/config/extapps/webserver) و [محدودیت اتصال هر IP](https://www.litespeedtech.com/docs/webserver/config/security) مستندند، ولی مقدار واقعی این هاست هنوز مشاهده نشده است. به‌ویژه اگر شرکت‌کنندگان پشت NAT سالن باشند، بررسی محدودیت هر IP اهمیت دارد؛ هیچ حفاظت امنیتی در این نوبت غیرفعال نشد.
5. برای کاهش رفت‌وبرگشت حساس Ultimatum، endpoint سازگارِ resolve فعلی + prepare بعدی و ارسال دسته‌ای رخدادهای کمکی بررسی شود؛ ترتیب، randomization، RT و زمان انتظار باید حفظ شوند. این کار هنوز پیاده‌سازی نشده است.
6. پس از شناسایی و اصلاح گلوگاه مشخص، آزمون عمومی ۶۰۰ با کنترل رکوردهای هر run و آزمون مرورگر/قطع شبکه تکرار شود. انتقال به Production فعلاً تأیید نشده است.

## وضعیت Production و پایان کار

Production در جریان و پس از بعضی آزمون‌ها health متناوب داشت. اتصال مستقیم دیتابیس در بررسی قبلی سالم بود؛ restart معمول Passenger، پنج health متوالی را سالم کرد. در بررسی پایانی این نوبت، دو probe ده‌ثانیه‌ای timeout و probe بعدی HTTP 200 بود. بنابراین آخرین پاسخ آن موفق است، اما مشکل سلامت متناوب حل‌شده محسوب نمی‌شود و نمی‌توان آن را صرفاً به ساختار جدید Staging نسبت داد. نسخه، .htaccess و backend اصلی تغییر نکردند.

Staging در سه بررسی پایانی HTTP 200 و اتصال PostgreSQL سالم داشت و از Uvicorn پاسخ می‌داد. Supervisor RUNNING بود. تمام بارها، مانیتورهای موقت و تونل تشخیصی بسته شدند؛ سرویس Staging و @reboot آن عمداً باقی ماندند. هیچ تغییر کد برنامه به GitHub push و هیچ PRی merge نشد.
