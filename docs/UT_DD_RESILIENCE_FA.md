پایداری اولتیماتوم و DD — طرح و ثبت اعتبارسنجی

مبنای تغییر PR #27 با commit `5a823e874406cd6804fba5af45f232432bf383fe` بود. سورس نهایی برنامه `68d22169d8d599d4fe6bc2034873c6a58ab7f593` روی Staging منتشر و در مسیر عمومی بررسی شد. CI همان commit موفق است: https://github.com/Rezaaoow/barsan-experiment/actions/runs/41623720309 . این سند ابتدا پیش از توسعه نوشته و سپس با شواهد واقعی تکمیل شده است.

دامنه: IndexedDB با تراکنش و migration از localStorage برای DD و اولتیماتوم، ارسال زمان‌های کمکی بدون await شبکه در مسیر ادامه، هم‌پوشانی resolve و انتظار مقرر، prefetch دور بعد، تکمیل بازیابی‌پذیر و دادهٔ ساختاریافتهٔ افزایشی بدون حذف payload/ستون قدیمی. پرسشنامه و طرح آزمایش تغییر نمی‌کنند.

قواعد صحت: ack فقط revision ارسال‌شده را پاک می‌کند؛ رخداد تازهٔ همان round هنگام درخواست در حال اجرا باقی می‌ماند. هیچ مقدار secret در outbox یا لاگ تازه ذخیره نمی‌شود. دادهٔ قدیمی فقط بعد از commit مهاجرت پاک می‌شود. شکست storage به معنی صف خالی نیست. retry همان شناسه و همان نتیجه را بازیابی می‌کند. تصادف و امتیاز سمت سرور می‌مانند. refresh تسک ناقص همچنان attempt تازه است و بازیابی تصمیم قبلی پیش از supersede انجام می‌شود.

آزمون لازم: IndexedDB واقعی در مرورگر، مهاجرت/بازشدن مجدد/abort تراکنش/revision، قطع و وصل شبکه، حذف پاسخ پس از commit، زمان‌های کمکی بدون توقف UI، تکرار و هم‌زمانی resolve/prefetch، تطبیق ۲۲ دور اولتیماتوم و ۳۰ DD، خروجی قدیم و جدید، SQLite و PostgreSQL و CI دقیق commit. Staging تنها مقصد مجاز deploy است؛ Production تغییر نمی‌کند. بار بالا فقط پس از دسترسی سالم و guard محیط انجام می‌شود.

پیاده‌سازی انجام‌شده:

1. صف تراکنشی مستقل در `app/persistence.js`؛ مهاجرت تأییدشدهٔ صف‌های DD و تصمیم/رخداد اولتیماتوم، حذف فقط revision تأییدشده، تشخیص خرابی ذخیره و آزمایش نوشتن/خواندن پیش از تسک. دعوت‌نامه و توکن admin در صف جدید ذخیره نمی‌شوند.
2. دو مسیر ارسال محدود: تصمیم اصلی پشت درخواست کمکی معطل نمی‌شود؛ پاسخ‌های DD در مسیر پس‌زمینه بر زمان‌های کمکی اولویت دارند. backoff/jitter و شناسه‌های idempotency قبلی حفظ شده‌اند. timeout اکنون خواندن بدنهٔ پاسخ را نیز پوشش می‌دهد.
3. ادامهٔ اولتیماتوم فقط منتظر commit محلی زمان‌هاست. ارسال زمان‌ها همراه resolve بعدی یا completion انجام می‌شود؛ مسیر batch حداکثر ۲۵ دور، با اعتبارسنجی مالکیت و تراکنش atomic، مکمل بازیابی است. اولین زمان ثبت‌شده در retry حفظ می‌شود.
4. resolve پیشنهاددهنده پس از commit محلی، در طول انتظار مقرر شروع می‌شود. نمایش زودتر از پایان انتظار مجاز نیست. مدت واقعی انتظار بعداً با رخداد پایان انتظار ثبت می‌شود؛ timestamp گم‌شده جعل نمی‌شود.
5. prefetch دور بعد از نتیجهٔ سروری، با همان کنترل ترتیب/تمرین/بلوک و نتیجهٔ تصادفی پایدار. خطای prefetch پاسخ ثبت‌شده را ناموفق نمی‌کند و مسیر prepare قبلی به‌عنوان fallback باقی است.
6. intent تکمیل DD/UT در IndexedDB، بازیابی بعد از reload، retry خودکار محدودشده با backoff و دکمهٔ تلاش مجدد. DD پیش از completion نیازمند ۳۰ پاسخ ثبت‌شده است. شکست ارسال نهایی به معنی تکرار تسک نیست. refresh تسک رفتاری ناقص همچنان طبق قاعدهٔ قبلی attempt تازه می‌سازد.
7. قفل یک شرکت‌کننده در تب‌های یک مرورگر؛ کنترل run سمت سرور همچنان مرجع دستگاه‌های دیگر است. پرچم پنهان‌شدن تب برای اولتیماتوم به metadata افزوده شده است.
8. خروجی‌های مرتب نسخهٔ ۲ برای هر دو تسک در پنل مدیریت؛ raw payload، ردیف قدیمی و خروجی قبلی حفظ شده‌اند. نمای منظم هنگام خروجی ساخته می‌شود، بدون افزایش write هر پاسخ برای یک کپی JSON دیگر. ستون‌های context از اطلاعات معتبر سرور ساخته می‌شوند.
9. فونت متغیر Vazirmatn همان نسخهٔ v33.003 روی دامنهٔ برنامه، با cache نسخه‌دار و license اصلی؛ blob رسمی `a501289a85595158570b0c2badcb4608b042e748` بررسی شده است. dependency روی CDN از صفحهٔ شرکت‌کننده برداشته شده است.

اعتبارسنجی محلی تا این مرحله: ۹۹ تست SQLite/API/مرورگر موفق؛ هشت مورد مرورگر با IndexedDB واقعی و Chrome جداگانه اجرا شدند. آزمون کامل مرورگر ۲۲ دور را با یک prepare و ۲۲ resolve تکمیل کرد؛ در پایان رخدادهای زمانی لازم در سرور ثبت و صف همان run خالی بود. زمان‌های پژوهشی فقط در harness این تست به ۵ms کاهش داده شدند تا کنترل جریان آزموده شود؛ این عدد نتیجهٔ latency هاست یا تغییر runtime نیست. یک تست مستقل با انتظار ۲۵۰ms بررسی کرد نتیجه زودتر از انتظار نمایش داده نشود و ارسال در طول انتظار آغاز شود.

PostgreSQL محلی مستقل نسخهٔ ۱۷: smoke قبلی، هم‌زمانی ۲۴ شرکت‌کننده، شروع‌های هم‌زمان و قرارداد کامل DD و هر دو شرط اولتیماتوم موفق شدند. قرارداد جدید پس از تکمیل قابلیت ارسال همراهِ زمان‌ها نیز با pool چهار و سقف هشت sync thread تکرار و موفق شد. CI شاخه Python 3.12 / PostgreSQL 16 و مرورگر Chromium را اجرا می‌کند؛ وضعیت دقیق CI در GitHub همان commit بررسی شود. نسخهٔ Python محلی 3.13 است.

پیش از افزایش بار، یک smoke دونفرهٔ هر دو شرط موفق شد. هر مرحله fixture مستقل داشت؛ ۱۰۰۲ تخصیص مصنوعی و ۸ گروه در پایان غیرفعال شدند. صفر ردیف پژوهشی حذف شد. در cohort ششصدنفره، ۱۸۰۰۰ DD و ۱۳۲۰۰ UT، ۱۲۰۰ run و ۱۲۰۰ مرحلهٔ workflow تکمیل بودند؛ مدت انتظار واقعی و زمان کلیک ادامه برای هر ۱۳۲۰۰ دور موجود بود. در کل چهار cohort، ۴۲۰۷۷ درخواست با صفر شکست HTTP و صفر retry ثبت شد؛ quantileهای cohortها میانگین گرفته نمی‌شوند. تعداد prepare دقیقاً یکی برای هر شرکت‌کننده بود. خروجی k6 برای هر چهار نوبت exit code صفر داشت.

در مرحلهٔ ۶۰۰، p95 برنامه حدود ۲۰۷٫۳۲ms، checkout pool حدود ۲۵٫۹۲ms و SQL حدود ۲۴٫۶۹ms بود؛ این quantileها هم‌پوشانی دارند و نباید جمع شوند. generator روی همان حساب هاست و با GOMAXPROCS=2 و GOMEMLIMIT=1GiB اجرا شد؛ بیشترین RSS مشاهده‌شدهٔ خودش ۴۳۶٫۲۳MiB بود. fixture با SharedArray بین VUها مشترک بود. در کل ۹۵ بررسی محافظ سلامت Production شکست دیده نشد. این موفقیت، مشکل متناوب تاریخی Production را برای همیشه حل‌شده ثابت نمی‌کند.

مرورگر جداگانه روی دامنهٔ واقعی Staging، HTML جدید، فونت محلی و ماندگاری IndexedDB بعد از reload و قطع اتصال را بررسی کرد؛ دادهٔ آن فقط probe محلی ساختگی بود و هیچ حساب شرکت‌کننده از هاست منتقل نشد. یک baseline جدا از Mac، ۲۴ درخواست health با صفر خطا، median حدود ۷۹٫۲۹ms و p95 حدود ۱۴۶٫۸۶ms داشت؛ این فقط health و یک اینترنت است، نه latency مسیر کامل شرکت‌کننده.

حدود اعتبار: این آزمون API از یک مبدأ داخل هاست است؛ ظرفیت ۶۰۰ مرورگر/۶۰۰ اینترنت واقعی از آن نتیجه نمی‌شود. شروع VUها در پنجرهٔ تصادفی ۳۰ ثانیه پخش شد. DD پنج پاسخ مصنوعی در هر ۷٫۵ ثانیه فرستاد؛ این زمان‌بندی ابزار بار است، نه تغییر زمان محرک در مرورگر. انتظار رقیب اولتیماتوم در آزمون‌های بار ۲ ثانیه / حدود ۳ تا ۶ ثانیه باقی بود؛ فقط smoke دونفره برای بررسی قرارداد API شتاب داده شد. اثر مصرف منابع خود generator و تفاوت payload مصنوعی با مرورگر واقعی در تفسیر نتایج باقی است. نخستین نمونهٔ جدید پیش از ساخت cohort به علت مقدار قدیمی توکن در فایل محیط متوقف شد؛ پس از backup خصوصی، فایل با همان credential از قبل فعال هماهنگ شد، بدون تغییر توکن فعال یا افشا/انتقال آن.

پشتیبان مستقل دیتابیس با pg_dump 13.23، فهرست pg_restore و source backup پیش از انتشار تأیید شدند و در پوشهٔ خصوصی هاست ماندند. انتشار با توقف سرویس، تعویض هماهنگ فایل‌ها، شروع، readiness و تطبیق public HTML/font/runtime hash انجام شد. کد/تنظیمات Production تغییر نکرد و هیچ PR merge نشد. metadata انتشار روی هاست به سورس برنامهٔ 68d22169 اشاره می‌کند؛ commitهای گزارش/ابزار بعد از آن تغییر runtime نیستند.

حفظ پاسخ محلی جای پاسخ سرور برای نتیجهٔ اولتیماتوم را نمی‌گیرد؛ قطع کامل یا طولانی هاست همچنان ممکن است انتظار کنترل‌شده ایجاد کند. زمان فعال workflow روش حسابداری قبلی و سقف ۴۵ ثانیه را دارد و زمان دقیق آفلاین را بازسازی نمی‌کند. پایلوت مرورگر/شبکهٔ نمایندهٔ شرکت‌کنندگان پیش از انتقال به Production همچنان لازم است. شواهد عددیِ فاقد token/هویت/پاسخ فردی در `artifacts/ut-dd-resilience-20261103/` است؛ لاگ و fixture خصوصی به خروجی یا مخزن منتقل نشده‌اند.


پرسشنامه، تعداد دورها، محرک‌ها، زمان‌های مقرر، مدل تصادفی رقیب، امتیازدهی و ترتیب تخصیص‌یافته تغییر نکرده‌اند. API جدید همهٔ فیلدهای خام قبلی را حفظ می‌کند؛ فعلاً هیچ فیلدی به قصد سبک‌سازی حذف نشده است.

پس از پایان آزمون و توقف guard، در بررسی پایانی Production قدیمی دوباره timeout داد؛ هم‌زمان Staging عمومی و loopback پاسخ ۲۰۰ و چند میلی‌ثانیه داشتند. با یک restart معمول Passenger (فقط restart.txt)، Production بازیابی شد و سه probe پیاپی ۲۰۰ بود؛ اولین probe حدود ۱٫۸۷ ثانیه و دو بعدی حدود ۶ms بودند. هش backend، HTML و .htaccess Production قبل و بعد ثابت ماند. این restart انتشار کد نیست؛ مشکل متناوب نسخهٔ قدیمی Production حل دائمی اعلام نمی‌شود. شواهد در `production-post-load-recovery.json` است.
